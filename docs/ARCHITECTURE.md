# LawDB architecture and decisions

## Shape

```
visitor / admin / (soon) firm owner
        |
   Cloudflare edge  --  static pages (HTML/CSS/JS/images), served directly, free
        |
   Worker (/api/*)  --  src/worker.js router -> src/routes/{public,auth,admin}.js
        |
   D1 (SQLite)      --  firms, blog_posts, leads, users, sessions, login_tokens, audit_log
        |
   Brevo            --  transactional email (sign-in links), sender info@lawdb.ca
```

## Decisions

| Decision | Why |
|---|---|
| Cloudflare Workers + D1, no servers | Scales globally and to zero, no ops, cost grows with usage. Fits the existing deploy. |
| Static pages stay static; only `/api/*` runs code | Fast and cheap for SEO pages; the database is only hit when needed. |
| One user table with roles (`admin`, `member`) | The same login will serve firm owners later. No second auth system. |
| Passwordless email links, no passwords | Nothing to leak or reset. Tokens are 256-bit random, stored only as SHA-256 hashes, single use, 15 min. |
| Link opens a page; a button POSTs the token | Email scanners that pre-fetch links cannot burn the one-time token. Token is in the URL `#fragment`, never sent to servers or logs. |
| Sessions in D1, HttpOnly + SameSite=Lax + `__Host-` cookie, 14 days | Revocable server-side (logout deletes the row); cookie unreadable by scripts. |
| Only known users or `ADMIN_EMAILS` can receive a link; always answer `ok` | No account enumeration, and strangers cannot make us email arbitrary addresses. |
| Same-origin check on every non-GET API call | CSRF protection on top of SameSite. |
| `data` JSON is the source of truth for a firm; indexed columns are derived | The API returns the exact shape the website already uses. |
| Whitelisted editable fields with validation | Admin edits cannot corrupt ratings, slugs or coordinates. |
| Append-only `audit_log` for every admin write | Accountability, and a base for firm-owner activity later. |
| Admin UI is plain JS with a strict CSP (no inline script, no third-party) | No build step to maintain; visitor text is only ever inserted as text, never HTML. |
| Migrations in `migrations/`, applied automatically on deploy | Schema changes are reviewed in PRs and cannot drift between environments. |
| CI runs migrations, seed and an end-to-end smoke test | Auth and security rules are regression-tested on every change. |

## How public pages read the database

The site was built with the firm list baked into the pages. Rather than rewrite 65 pages, the Worker swaps the
live list in on the way out (`src/routes/dynamic.js`):

- `/firms_data.json`, `/blog_data.json`, `/firms_hours.json` are served from D1 (used by search suggestions,
  the map's opening hours and the blog lists).
- `/find-lawyers`, the province hubs (`/alberta/`, `/manitoba/`) and every city hub (`/<province>/<city>/`) carry the
  whole firm list in an inline `<script>`. The Worker replaces that one line with the database's list.
- The results panel (list beside the map, bottom sheet on phones) is drawn by `lawdb-map.js` / `lawdb-map.css`, one shared file for every location page.
  It shows 10 firms a page with a dark page bar (`PER` in `lawdb-map.js`); the map keeps every pin. The bar goes back to page 1 whenever the
  list changes (filter, sort, area, new search) and a pin on another page opens that page. The bar sits in the list right after the tenth firm.
  Each card is one link to the firm's LawDB profile (the name's link is stretched over the card); Call, Directions and the firm's own Website button sit on top of it. Bump the `?v=` on both files in every page when either changes (`scripts/test-map-pages.mjs` checks that all 65 pages agree).
  The page reads top to bottom: an eyebrow and the page's own h1 (a city or province page keeps its `.city-hero` h1 for search engines and the script only styles it and puts the place in gold italic; the Find page gets "Trusted legal help, near you."), the search pill with a filter button beside it and the filter chips, then the map card. On a phone the sheet's full state tucks the heading away (`body.gm-full`) so the list gets the screen. The map's colours are the site palette (`P` in `lawdb-map.js`; pins are navy, featured pins gold, clusters dark gold `#8a6224` with a white ring and white numbers (5.4:1; the lighter gold `#c9a050` would be only 2.4:1 under white). The list is cream with a white card per firm: a navy tile with gold initials (or the firm's logo), serif name, rating then stars, the address with a pin, and a chevron. "Search this area" sits bottom-left over the map.
- **Profiles box.** A firm's social profiles (`data/firm-socials.json`, found on the firm's own website and looked at by a person; stored as `social` on the firm record, 638 firms) show on its page as a bordered "Profiles" box of large brand-coloured icons right under the firm's description (where the description would be, for a firm without one), like MSPdatabase (`src/render/profiles.js`). A database page renders it itself; a hand-built page gets it from the Worker (`withFollow` in `src/routes/firm-page.js`, placed after the page's `div.article`, from the same record). `cleanSocial` re-checks every address before it is shown, links are `noopener nofollow`, and a firm with its own LinkedIn page loses the generic "Find on LinkedIn" search link. `scripts/test-profiles.mjs` covers it.
- **Logo on a hand-built page.** A hand-built page has its logo baked into the file (a firm without one shows initials), so a logo saved later in the admin or owner screens (`type: 'logo'`, `src: 'img/<id>'` on the firm record; search, cards and the map already read it) used to show everywhere except on that page. The Worker now swaps the page's `<span class="li-logo">` contents for the record's logo on every request (`staticLogoHtml` in `src/render/logo.js`, applied in `src/routes/firm-page.js`; absolute address, same markup as the database page). A firm without a saved logo keeps the file's own. `scripts/test-static-logo.mjs` and a smoke step cover it. The cover photo and the written fields (description, hours, phone) are still read from the file on a hand-built page: edits to those show on the database page only.
- **LawDB's own social profiles** (X, Facebook, LinkedIn) are a row of icons under the footer blurb on every page (grey, white on hover, through the footer's own link colours), a "Follow LawDB" row under the Contact form, and the home page's Organization `sameAs` list plus `twitter:site`. `scripts/apply-site-socials.mjs` is the one place that holds the addresses and icons; it adds them idempotently and `--check` (in `npm run check`) fails if a page lacks them, so a new page copied from an old template cannot miss the footer row. The footer markup is also in `src/render/firm-chunks.generated.js` (regenerated from the reference firm page), which is how database firm pages get it.
- **Search that never dead-ends.** The home page and Find Your Lawyer search box (`suggest.js`), the box inside the map (`lawdb-map.js`) and the page's own parser (`find-lawyers.html`) all know the 62 cities that have firms. Anything else a person types is looked up in `places.json` (about 9,400 towns of the five provinces within 250 km of a firm, from GeoNames, CC BY 4.0, built by `scripts/build-places.mjs`; credit is on the Terms page) through `lawdb-places.js`, which is fetched only when a few letters are typed. A place answers as the "near a spot" search (`?near=Keswick%2C+ON&case=criminal`): `find-lawyers` lists the 40 firms closest to it, nearest first, with the distance, and the map is framed around the spot and the few firms really close to it (`fitAround` in `lawdb-map.js`). "Lawyers near me" and the map's locate button use the same mode with `?near=me`; the position is read in the browser and never goes into the address or to the server (the home page hands it to the results page through `sessionStorage`, `lawdb.near`, for 30 minutes). If fewer than three firms of the practice area are within 150 km, every kind of firm is listed and a note says so. `scripts/test-places.mjs` checks the lookup and the distances.
- **Live totals.** Any page with `data-live="firms"`, `data-live="cities"` or `data-live="city:PROV|City"` (the home page, For Law Firms and the home page's Browse-by-city chips) has those numbers rewritten at the edge from the database (`withLiveStats` in `src/routes/dynamic.js`; `/` and `/for-firms` are in `run_worker_first`). The numbers typed in the files are only the fallback, so a firm that lists itself or a released batch never leaves a stale total. `scripts/refresh-hub-counts.mjs` still bakes the per-city and per-province counts into the hub pages' text (crawlers and no-database fallback); it is run when a batch is released.
- **Lighter pages.** The list sent to browsers leaves out fields nobody reads (`DROPPED_FIELDS` in `src/routes/dynamic.js`: the Maps link, blurb, firm-page pictures and the Directions link, which the page rebuilds from the address). A city page or province hub carries only its own province's firms (`var LAWDB_SCOPE`); `lawdb-map.js` fetches the rest of `/firms_data.json` the first time the search box is focused, so a firm in another province can still be found by name. `/find-lawyers` carries everyone. At 1,092 firms a Toronto page went from about 900 KB to about 340 KB (72 KB compressed), Calgary to about 170 KB.
- Responses are cached at the edge for 60 seconds (`PUBLIC_CACHE_TTL`, seconds; 0 disables), so a busy site reads the
  database about once a minute per location, not once per visitor.
- **Safety net:** if the database cannot be read, or a page does not contain exactly one inline list, the original
  static file is served unchanged. The pre-built JSON files and pages stay in the repo as that fallback and as the seed.
- `run_worker_first` in `wrangler.jsonc` lists the paths that reach the Worker; everything else is served as free static files.
- CI proves the database output equals the static files byte-for-byte (as data), preserves order, and that an admin edit
  appears on the public pages.

## Firm profile pages (`/firms/<slug>`)

Each firm has a `page_mode` column:

- `static` (default for all 370 original firms): the hand-built HTML page is served unchanged, so nothing looks different
  until a firm is switched.
- `dynamic` (default for firms created in the admin area): the Worker renders the page from the database
  (`src/routes/firm-page.js` + `src/render/firm-page.js`). The page skeleton (header, cover, services, hours card, guide,
  carousel, lead form, footer) is extracted verbatim from the existing pages by `scripts/extract-firm-template.mjs` into
  `src/render/firm-chunks.generated.js`; `npm run check` fails if that file drifts from the source pages.

Writing for a firm page lives in the `about` column (kept out of the `data` JSON so the public firm list stays small).
`migrations/0004_import_about.sql` and the seed fill it from the existing pages. Firms are created with
`POST /api/admin/firms` (admin form "Add a firm") and can be switched either way from the edit form. Profile pages are
cached 60 seconds like the other public pages, and fall back to the static file if the database cannot be read.
`/firms/*` therefore always passes through the Worker.

The richer tabbed layout of the six firms that were Featured at launch is not reproduced by the dynamic template; keep those on `static` for now. Only two firms are Featured today (Blottman Legal Services and Barbarian Law, which have a commission arrangement with LawDB); the other four (Daniel Brown Law LLP, Nelligan Law, Amlea Avocats, Gagan Nahal Criminal Lawyer) are basic listings that keep the layout but have no tick, "Featured on LawDB" line or badge anywhere. `firms_data.json` and the lists baked into the static pages carry the flag as a fallback (Gupta Law Firm was never Featured in the database, but its baked-in entries and its home page card said so; they were corrected); the live database was changed once by `migrations/0030_unfeature_partners.sql` (a migration, not an update file, so a firm that pays for Featured later is never switched off again).

The per-practice-area pages are still pre-built HTML.

Capacity note: the Worker now handles these page views. On the free Workers plan that is 100,000 requests a day; the
Workers Paid plan ($5/month) raises it to 10 million a month. Plain static pages remain free and unlimited.

**Book a call button** (`src/lib/booking.js`, `src/render/booking.js`, `scripts/apply-firm-booking.mjs`, `data/firm-booking.json`, `db/booking-updates.sql`): every firm page, hand-built or database-built, has a "Book a call" button under Call / Website / Directions (the Worker adds it in `withFollow`, so both page types get it, and the snippet carries its own style). A firm with a `bookingUrl` in its data gets an active light-gold button that opens the link in a new tab (`rel="noopener nofollow"`); every other firm gets the same button greyed out, and tapping it (`follow.js`) opens a note that points the firm to the "Claim this listing" line under the buttons (a firm that is already managed just reads that it has not added a link yet). `cleanBookingUrl` is the one rule for storing and showing a link: https only, no sign-in details, no address of this machine or LawDB itself, no email tracking redirects, and the month, `utm_*`, layout and fragment parts dropped. An owner or an admin sets or clears the link in the edit form ("Booking link", `FIRM_FIELDS.bookingUrl`), which is also how a firm unlocks the button. The first links came from a scan of every listed firm's own website (home page, plus its contact or consultation page when the home page had nothing): a calendar (Calendly, Clio Scheduler, Microsoft Bookings, Acuity, Setmore, Google Calendar and similar) or a page or form the firm itself labels "Book" or "Schedule", each opened to check that it loads (October 2026: about 1 firm in 4 has one; links that only point to a home page, another firm's site, or a login were left out, and so were pages that only offer a generic "request a consultation" form). `apply-firm-booking.mjs` writes `bookingUrl` on the batch records and `db/booking-updates.sql` (loaded by `db:updates:*` and `deploy:ci`), which fills a firm only while it has no link, so a link typed in the admin or owner form is never replaced. `npm run check` fails if the data file, the records or the SQL drift, or if a stored link is not clean. Clicks are counted as `book` and `book-locked` (a tap on a greyed-out button, i.e. people who wanted to book with a firm that has no link) in the Traffic tab. `bookingUrl` is left out of the public firm list (`DROPPED_FIELDS`).

## Firm owners (Phase B)

- **Sign-up:** `/account/` is the owner area. The same one-time email link signs in or creates a plain `member` account
  (`signup: true` on `/api/auth/request-link`). Brand-new addresses are limited to 6 links per requester per hour and
  150 per day (Brevo's free plan sends 300 emails a day); a limit hit is logged as `signup.throttled`.
- **Nothing happens without approval:** `firm_members` holds one row per (person, firm) with status `pending`,
  `approved` or `rejected`. Owners ask to manage an existing firm (`POST /api/account/claims`) or submit a new one
  (`POST /api/account/firms`, stored with `firms.status = 'pending'` and hidden from every public query until approved).
  The admin approves or rejects on the Approvals tab; approving a new listing needs a map position (looked up from the
  address with OpenStreetMap when possible, otherwise entered by the admin). Approval can also switch a hand-built page
  to the database page so the owner's edits show on it.
- **What owners can do:** edit their own firm (same fields as admin except `featured`, page style and rating) and read/update
  the enquiries for it. Access is checked on every request against an approved membership of that exact firm.
- **Lead routing:** a form on a firm's profile page sends `firm=<slug>`; the lead is stored with `leads.firm_slug`, shown in
  the owner's dashboard immediately and emailed to the firm's approved owners (max 20 emails per firm per hour).
  The admin is emailed when a request needs approval, and the requester when it is decided.
- Shared code: `src/lib/firm-edit.js` (validation, create, edit), `src/lib/email.js` (all mail), `admin/ui.js` (UI helpers).
- Local development sends no mail; each message is recorded in the audit log as `mail.dev` instead.

## Owner invites and the Claim button
- **Invite (admin, after a phone call):** Admin, Firms, open a firm, "Give this firm to its owner". Enter the owner's email. `POST /api/admin/firms/:slug/invite` stores a hashed one-time token in `firm_invites` (14 days, limits: 5 per firm and 60 in total per day) and emails the link `/account/welcome#invite=<token>`. The admin also sees the link to copy or read out.
- **Accept:** the owner presses a button on `/account/welcome` (the token is POSTed to `/api/auth/invite-accept`, so mail scanners cannot burn it). One request atomically uses the token, creates the account if needed, makes them an approved owner of that firm, skips the member welcome steps, signs them in and opens `#edit/<slug>`. The invite can also switch a hand-built page to the database-built page so their edits show.
- **Claim button:** every live firm page shows "Is this your firm? Claim this listing" (or "Managed by the firm" when an approved owner exists), added by `withFollow` in `src/routes/firm-page.js`. Signed-out visitors get the centred sign-in popup, then land on the claim form for that exact firm (`/account/#find/<slug>`). Claims still wait for admin approval.

## Logo finder (admin, Logos tab)
- Firms that show initials instead of a logo (about 230 with a website). For each, `findLogos` (`src/lib/logo-finder.js`) reads the firm's own homepage for a logo-like image (an `<img>` named logo/brand, the site icon, the share picture), checks each candidate is a real JPEG/PNG/WebP of a usable size, and shows up to three. An admin presses "Use this logo" or Skip, so nothing is saved by itself and wrong pictures (partner badges, photos) are left out by a person.
- Previews go through `/api/admin/logo-preview` (the admin pages may not load other sites' pictures). Saving goes through the normal `addImage` checks. SVG is never used. Only public https addresses are fetched, every redirect is checked, and the first-bytes type check decides what a file is. Admin uploads are allowed up to 300 an hour.
- **Merging admin-saved logos into the repository.** A logo saved in the Logos tab lives in R2 and the database, so it shows in the directory, search and map at once, but a hand-built firm page (`page_mode` static) keeps its initials until the page file is updated. To bring them in: find the saves in the audit log (`image.add` with `kind: "logo"`, or `logo.from_site`, entity `firm`), download each picture from `/img/<id>` (public), look at it on a white page, save it as `images/logos/<slug>.<png|webp|jpg>` (shrink anything over about 100 KB or 800 px), add `{ src, site }` to `data/logos-existing.json`, take the slug off `data/logo-rejects.txt` if it is there, and run `node scripts/apply-existing-logos.mjs` (it swaps the initials badge, or a logo hot-linked from the firm's own site, on the page; `db/logo-updates.sql` only touches records still showing initials, so the uploaded logo is never replaced). A picture that is not the firm's own (a chamber of commerce seal, a partner or award badge) is left out. October 2026: 14 firms were merged this way.

## Blog cards for every firm
- Every live firm with a website gets a `firm_feeds` row (`ensureFeedRows`). A cron every 5 minutes (`feedBatch`) finds the blog of one firm that was never looked at (discovery is about 15 requests; a run may make 50), and re-reads up to 6 known blogs that are due. All 1,000+ firms are covered in under four days, then kept fresh.
- **Featured firms** (and any blog added by hand in the admin) are shown everywhere: LawDB News, a LawDB story page per article, the story sitemap, members' feeds.
- **Every firm's blog is on LawDB News** (migration `0025_news_all_blogs.sql` took everyone off `page_only`; new feed rows default to everywhere). Only **Featured firms' and hand-added blogs'** story pages are offered to search engines; everyone else's story pages work and can be shared but are `noindex, follow` (header and meta tag) and stay out of `/sitemap-news.xml`, because thousands of excerpt pages would lower the site's quality (`isIndexableStory` / `STORY_INDEXABLE_SQL` in `src/lib/stories.js`). `page_only` is now only an admin switch that holds one firm's blog to its own page. The visibility rule is still `(page_only = 0 OR featured = 1)` in the News, story and feed queries, so a Featured firm is always shown.
- Admins can flip a firm with `PATCH /api/admin/firms/:slug/feed {pageOnly}`; adding a firm to News by hand sets it to everywhere. Migration `0024_feed_page_only.sql`.

## Enquiries dashboard (a Featured benefit)
- Every enquiry from a firm page is still emailed to the firm's approved owners, on every plan.
- **Featured firms** get the dashboard at `/account/#leads`: numbers on top (new, 7 days, 30 days, all time), filters by status, search, a "new" marker and count on the tab, Reply by email / Call, status, a private note per enquiry, and an export to spreadsheet (`/api/account/firms/:slug/leads.csv`, formula-safe). Opening the list marks the enquiries as seen (`leads.seen_at`).
- **Basic firms** see only the counts and an upgrade prompt (`listLeads` returns `locked: true` with no personal details; changing and exporting return 403). The plan check is `isFeatured` in `src/lib/leads.js`.
- Mondays (every night when `DEV_ECHO_LINK=1`), the nightly job emails each approved owner whose firm had enquiries in the last 7 days a summary (`sendLeadDigests`; `firm_members.digest_at` stops repeats). Featured and Basic get different wording.
- Enquiry details, including notes, are blanked after 12 months by the nightly housekeeping. Migration `0023_lead_inbox.sql`.

## Blog cards ("Latest from the firm")

- Source: the firm's public RSS/Atom feed, found automatically from its website (`<link rel="alternate">`, then common paths like `/feed`) or entered by hand.
  Stored in `firm_feeds` (settings, status) and `firm_posts` (migration 0008): at most the 6 newest posts, each with a headline, date, a plain-text excerpt of at most 600
  characters and a link. Full articles are never stored or shown; if a feed only publishes full text, just the opening words are kept.
- Safety (`src/lib/feeds.js`): https only, no IP addresses or internal names, no logins or odd ports, every redirect re-checked, 8 s timeout, 1.5 MB cap; all markup is stripped;
  a post is kept only if its link points at the firm's own website (or the feed's host), so a feed cannot push links elsewhere.
- Display (`src/render/blog-cards.js`): up to 3 cards (headline, date, a short teaser that expands to the longer excerpt with a native `<details>` control, and a link to the article on
  the firm's site). Database-built pages include them in the template; hand-built pages get them injected at the edge with `HTMLRewriter` (after the "From the Firm" block, or
  before the fine print). Pages work unchanged if the lookup fails.
- Who gets them: Featured firms automatically (nightly cron `refreshAllFeeds`), any other firm when its owner or the admin switches them on. Owners and admins can switch cards off,
  enter the feed address, and check now (owners at most every 5 minutes) from the Blog cards panel. Local development never contacts real websites; it only re-reads feeds entered by hand.
- **Card pictures** (migration 0011, `firm_posts.image_url`): the picture the firm chose for each article. WordPress: the featured image (`_embed=wp:featuredmedia`, a medium-large size first, `jetpack_featured_media_url` as a backup;
  sites that refuse `_embed` are read the plain way). RSS/Atom: `media:content`, `media:thumbnail`, an image `enclosure`, else the first picture inside the item. Only the **address** is stored, never the file; it is loaded by the
  visitor's browser from the firm's own site (lazy, no referrer, 16:9 crop, dropped if it fails to load). Addresses must be public https (http is upgraded), no logins, no SVG/GIF, no tracking pixels; a picture repeated on several
  posts of one blog (a stand-in or logo) is ignored.

## Firm pictures

- Files live in the private R2 bucket `lawdb-images` (binding `IMAGES`, key `img/<id>`); the `firm_images` table (migration 0007) decides what is shown.
  The public address is `/img/<id>` (Worker route, cached 1 day in browsers). Only pictures still listed in the table, for live firms, are served; removal
  deletes the row and the file and clears the edge cache.
- Kinds: `logo` (one), `cover` (one), `photo` (up to 6). A new logo/cover replaces the old one. The logo and cover are written into the firm's public record
  using the fields the hand-built pages already use (`type: 'logo'`, `src: 'img/<id>'`, `heroImage`), so directory cards, the map, hubs and search show them; the
  original file names are remembered (`origSrc`, `origHero`) and restored when the picture is removed. Photos appear in a gallery on database-built pages.
- Upload safety (`src/lib/images.js`): the format is read from the file's own bytes (JPEG, PNG, WebP only, never SVG), 3 MB maximum, 64-8000 pixels per side,
  20 uploads per person per hour, owner descriptions pass the content rules. Pictures are served with `nosniff` and a sandboxing CSP.
- Admins can manage any firm's pictures; owners only their own. Every add/remove is in the activity log. The backup includes the `firm_images` rows; the files are in the bucket.

## Featured payments (Stripe)

- **No API key.** Stripe sends signed webhooks to `POST /api/stripe/webhook`; `src/lib/stripe.js` checks the `Stripe-Signature` header (HMAC-SHA256 with `STRIPE_WEBHOOK_SECRET`, 5-minute tolerance,
  constant-time comparison) before anything else. No secret configured = 503; bad signature = 400. Each event id is stored (`stripe_events`) so a repeat is applied once; a failure removes the id so Stripe retries.
- **Who gets Featured:** the owner's "Upgrade to Featured" button opens the Stripe payment link with `client_reference_id=<firm slug>` and `prefilled_email=<owner email>` (`STRIPE_PAYMENT_LINK`, one plan: $89/month).
  On `checkout.session.completed` the firm is made Featured only if the payer's email is an approved owner of that firm. Otherwise the payment is parked as `needs_review` (admin Payments tab: assign to a firm or dismiss).
- **Lifecycle** (`firm_subscriptions`, migration 0009): subscription events keep status (`active`, `past_due`, `canceled`), renewal date and cancel-at-period-end. `past_due` keeps the firm Featured while Stripe retries the card.
  When no live subscription remains the firm returns to Basic, unless it was already Featured before paying (`featured_before`, e.g. set by hand), which is never undone. Events may arrive in any order.
- **Owner side:** `GET /api/account/firms/:slug/plan` feeds the plan card (Basic/Featured, renewal date, upgrade link, manage-billing link from `STRIPE_PORTAL_URL`). **Admin side:** Payments tab, Overview totals (count and monthly amount).
- Setup steps for the live account are in `docs/STRIPE_SETUP.md`. Local tests sign events with `STRIPE_WEBHOOK_SECRET=whsec_smoke_test_secret` from `.dev.vars`.

## LawDB News and the menu

- **LawDB News** (`/news`, rendered by `src/routes/news-page.js` + `src/render/news-page.js`) is the page of member firms' blog cards: firm name (Featured badge), date, headline, a short preview that expands,
  and a link to the full article on the firm's own website. Filter by firm with `?firm=<slug>`. A static copy (`news.html`, built by `scripts/build-news-fallback.mjs`, checked by `npm run check`) is served if the database is down.
- **Page design** (from the owner's News mockup, in the palette): a plain cream header (gold "News & insights" eyebrow with a rule, the h1 "LawDB News", the line "Real stories. Practical advice. *All in one place.*", a short welcome that says the firms write the articles, and three real numbers: firms writing, recent articles, latest story date), "how it works" as three linked cards (two side by side and one wide on a phone, three across on a wide screen), "The firms writing here" as a grid of round logos (15, then "and N more" which jumps to the filter), the filter as one pill (a transparent `<select>` over it, so it works without scripts), then the feed. The counts and the firm list are computed from the database, never invented. (The earlier "The Press" masthead with the turning seal and the drifting story cards was removed for this design.)

## Traffic counts (admin Traffic tab)

Google Search Console is slow and says nothing about what people do once they arrive, so the site counts its own traffic, without tracking anyone.

- **What is counted** (`src/lib/stats.js`, migration 0028, table `stats_daily`): one row per Toronto day, kind and label with a running count. Kinds: `pv` page views, `visit` new visits, `entry` landing pages, `ref` referrers (search engines and social sites grouped), `dev` phone or computer (by screen width), `geo` country and province from Cloudflare's coarse location (new visits only), `utm` campaign links, `ev` clicks that matter (call, website, directions, follow, claim, and the Featured and List buttons, per page), `search` (kind of lawyer + city, province or "near me"), `town` and `noparse` (the words of a search that named a town with no page yet, or matched nothing).
- **What is never stored**: no IP address, no browser details, no cookie, no visitor id. Robots (`isBot`) and anyone sending Do Not Track or Global Privacy Control are not counted; the member, admin and API areas are never counted. Words are kept only when they are plain letters (numbers, emails and links are dropped), and a search that matched a city never keeps the extra words. A new visit is told from another page of the same visit by a note in `sessionStorage` (tab only, not a cookie).
- **The owner's own visits**: counting a phone or computer the owner uses would swamp the numbers, and an IP block cannot work (a phone's address changes all day, and no address is kept). Instead a note in that browser's own storage (`localStorage.lawdb_skip = '1'`, not a cookie, never sent anywhere) makes `site.js` send nothing. Opening `/admin` signed in as an admin sets it on that device unless it was already set to `'0'`; the Traffic tab's "Your own visits" card shows the state and switches it either way (to test the counters, for example). Visits counted before it was set cannot be removed, since nothing about a visitor is kept. Browsers that clear site storage (private windows) count the visit until the admin is opened again.
- **How it flows**: `site.js` (loaded on every public page) sends a small JSON message with `navigator.sendBeacon('/api/a')`; pages that run before it loads queue theirs on `window.lwq` (`find-lawyers.html` does this for searches, once in `runSearch` and once for `?near=`). `POST /api/a` (`src/routes/stats.js`) answers 204 whatever happens, checks the message against a whitelist (`eventIncs`), throttles one address to 90 messages a minute per isolate (nothing stored), and adds one to each counter in the background. Page views are counted in the browser because most pages are static files that never reach the Worker.
- **Reading it**: `GET /api/admin/traffic?days=7|30|90` (admin only) feeds the Traffic tab: visits per day, searches, towns people want that have no page (where to add firms next), searches that matched nothing, referrers, landing pages, regions, devices, most viewed pages and firms, and call/website/directions clicks per firm. The admin's content-security rules forbid `style=""` in markup, so the chart sets bar heights through the style object.
- **Retention** (nightly housekeeping, `prune`): counts 400 days, `town` and `noparse` words 90 days. The Privacy Policy describes all of this ("Visit and search counts"). The table is derived and is not part of the nightly backup.
- **Tests**: `scripts/test-stats.mjs` (cleaning, bots, throttle, what each message counts, retention SQL) is in `npm run check`; `scripts/smoke.mjs` sends real messages to the running Worker and reads the admin report.

  claims ("best", "#1", "top-rated", "guaranteed", "specialist"). Everyone who claims or adds a firm must accept the firm terms
  (`/terms#firm-terms`); the time is stored in `firm_members.terms_accepted_at`.
- **Reports:** every profile page links to `/report-listing?firm=<slug>`. Reports are leads with form `report-listing`; they are never shown
  or emailed to the firm. The admin is emailed. **Undo:** the Activity tab can restore the values an edit replaced (`POST /api/admin/audit/:id/revert`).
- **People:** the People tab disables/enables owner accounts (disabling ends all their sessions). "Sign out everywhere" is available to everyone.
  `ADMIN_EMAILS` is authoritative on every request: removing an address demotes that admin immediately.
- **Abuse limits:** 15 enquiries per requester address per hour (hash kept 7 days), 20 enquiry emails per firm per hour, sign-up limits (see above).
- **Backups and housekeeping:** a Cloudflare cron (`07:17 UTC`, `wrangler.jsonc`) runs `src/lib/backup.js`: it applies the retention rules, then copies every table into the
  `lawdb-backups` KV namespace (binding `BACKUPS`, each key expires after 35 days). "Back up now" is on the Overview tab; a stale backup or failed
  emails show as warnings there. D1 also keeps 30 days of point-in-time history (restore with `wrangler d1 time-travel restore`).
  **Retention (stated in the privacy policy):** enquiry personal details removed after 12 months (firm, date and status kept), abuse hashes 7 days,
  activity log 24 months, backups 35 days.
- **Health:** `GET /api/health` answers 503 if the database cannot be read; point an uptime monitor at it.
- Local test of the nightly job: `wrangler dev --test-scheduled`, then request `/__scheduled`.

- Batch 1 (100 firms) was collected from Google Maps listings for lawyers in cities that already have a hub page, keeping only firms that are open, have a phone number and a website, are rated 4.6 or better from at least 20 reviews, and are not already listed (matched on phone, name and website). Winnipeg was done first (hub plus all eight practice pages, checked 2026-10-21); a city is added by adding its entry to the data file and re-running the script. Re-check a city's sources about once a year, or when a court or agency moves.
- **Staged release:** `data/release.json` (`{ "released": [1, 2] }`) lists the batch numbers that are live. `build-extra-firms.mjs` only loads those batches into `db/extra-firms.sql`; the rest sit in the repository (logos included, not linked from anywhere) until a number is added and the change is merged. Release about a hundred firms at a time and watch Search Console (Indexing, Pages) for a week before the next. Batches 2 to 5 (309 firms, each with its own logo) were collected the same way as batch 1 (a second round of Google Maps searches across the hub cities); firms without a usable logo, or whose logo was rejected by eye, are kept unpublished in `data/reserve/firms-no-logo-N.json`. Descriptions taken from firms' websites are kept only when they read as plain statements of what the firm does (no phone numbers, calls to action, awards or superlatives).
- **Cover and bio pictures:** `node scripts/find-firm-photos.mjs` collects each firm's own share picture, a person chooses which ones to use (`data/firm-photos.json`: `{ slug: { kind: 'cover' | 'bio', src, from } }`), and `node scripts/apply-firm-photos.mjs` puts them on the hand-built pages, the batch records and `db/photo-updates.sql` (hand-built firms too, so their record is ready when they move to the database page). A picture that was first kept as a bio picture because it did not fit can be used as the cover: the cover is a face-aware 2.3:1 crop saved in `images/hero/`, the entry gets `bio` (the old bio path), and the apply script takes the bio picture off the page and the record. Crops narrower than 700 px, close-ups where the face does not fit the banner, and pictures with frames or cut-off people stayed bio pictures. **Second pass (own-site pictures):** `node scripts/find-firm-covers.mjs <out-dir>` goes through each cover-less firm's own pages (home, about, team, contact, up to a few pages, robots.txt honoured) and collects every real photograph that could be a banner (not logos, icons, badges, award or social images, flat or tiny images, or a picture shared by several firms), with a face-aware 2.3:1 crop proposal; a person looks at the contact sheets and picks the best picture per firm (real offices, buildings, teams and portraits, or fitting legal stock; no logos, text-heavy graphics, ads, other firms' branding or dark and broken images). Chosen pictures are saved as `images/hero/<slug>.webp` (at most 1400 px wide, around 60 KB) with a normal `{ kind: 'cover', src, from }` entry; a firm that already has a bio picture gets a second entry `<slug>+cover`. The pictures belong to the firms: a firm that wants one taken off or replaced does it through the claim flow, and `data/firm-photos-removed.json` removes a picture for good.
- **Hours:** `node scripts/find-hours.mjs` reads opening hours firms publish in their own website's schema.org data. Only plausible office hours are kept (Monday to Friday all open, five or six days, no "open 24 hours" and no identical seven-day week, which are usually a template default). `node scripts/apply-found-hours.mjs` adds them to `firms_hours.json`, to the firm's page (an hours card marked "Hours as listed on the firm's website"), and to `db/hours-updates.sql` (fills only firms with no hours yet). For batch firms the hours go into the batch record.
- `npm run deploy:ci` runs both SQL files after the seed; `npm run check` fails if either script has not been applied. Both are safe to run again.
